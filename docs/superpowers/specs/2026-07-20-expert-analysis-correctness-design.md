# Экспертный анализ: правильность, полнота, чистый вывод — дизайн

Дата: 2026-07-20. Согласовано с пользователем.

## Проблема

Экспертный анализ (`expert_reconciliation.py`) пропускает реальные операции и создаёт дубли:

1. Промпт требует «не более 8 расхождений» и группировку — Claude пропустил 4 реальные операции
   (09.02.2026 — 11 845; 27.02.2026 — 5 850; 26.03.2026 — 6 893; 30.03.2026 — 8 000).
2. `max_tokens=2800` — на большие акты не хватает.
3. Нет проверки полноты ответа.
4. Одна операция может вернуться в двух категориях; серверная переклассификация
   (`_downgrade_false_confirmed_missing`) не удаляет получившиеся дубли (случай 4 559 руб.).
5. Не проверяется, что влияние `likely_date_pair` равно 0.
6. Не проверяется окно дат (Claude писал, что 15 дней превышают окно 37 дней).

## Решение (согласовано)

Выводы формирует Claude; сервер добавляет программные защитные проверки с **автоисправлением**
(выбор пользователя). Расход токенов может вырасти — приоритет правильность.

### А1. Промпт и лимиты

- Убрать из `EXPERT_SYSTEM_PROMPT` лимит «не более 8 расхождений» и указание группировать.
  Каждое расхождение — отдельной строкой со своим evidence.
- `max_tokens`: 2800 → 8000.
- Запретить в `conclusion` пересказ отдельных расхождений (они уже в таблице):
  только общий вывод — сошлись ли сальдо, характер расхождений, итоговая сумма.

### А2. Проверка полноты + дозапрос

Новая функция `_find_unexplained_rows(row_index, report, scope)`:

- Программно строит множество строк, имеющих пару в другом документе по модулю суммы
  (жадное 1:1 сопоставление, допуск 0.01; повторно использовать строку нельзя).
- Строки без пары и суммой ≥ `min_amount`, не упомянутые ни в одном `resolved_evidence`, — «пропущенные».
- Строки сальдо/итогов в проверке не участвуют (в payload их и так нет).

Если пропущенные есть — дозапрос Claude: тот же системный промпт + пометка, что это доанализ,
payload содержит только пропущенные строки обеих сторон (для контекста — компактный список уже
найденных расхождений). Результат добавляется к отчёту, затем снова guard-проверки.
Максимум **2** дозапроса; если после них остались пропущенные строки — каждая добавляется
программной строкой категории `ambiguous` («Требуется проверка», влияние 0, reason
«Строка не объяснена экспертным анализом») с evidence на эту строку.

### А3. Защитные проверки (guards), порядок применения

Функция `_apply_expert_guards(report, row_index, scope)` после `resolve_expert_evidence`
и `_downgrade_false_confirmed_missing`:

1. **Окно дат**: для `likely_date_pair` вычислить разницу дней между evidence-строками;
   окно — `date_window_payment` для оплат, `date_window_delivery` для поставок
   (семейство по `_document_family`). Разница больше окна → категория `ambiguous`,
   reason дополняется «разница N дн. превышает допуск M дн.».
2. **Форма `likely_date_pair`**: обязательны evidence обеих сторон с равным модулем суммы;
   иначе → `ambiguous`. Для валидных пар влияние принудительно 0.
3. **Влияние `confirmed_missing`**: должно равняться сумме evidence-строки с учётом знака
   стороны (doc1: debit +, credit −; doc2 зеркально — как в программной сверке);
   расхождение больше 0.01 → влияние исправляется по данным акта.
4. **Дедупликация**: две записи, ссылающиеся на одну и ту же строку акта
   (`(side, row_id)` пересечение resolved_evidence), — остаётся одна по приоритету:
   меньший индекс категории в `EXPERT_CATEGORY_ORDER`, при равенстве — больший модуль влияния.
   Выполняется **после** переклассификаций (закрывает дубль 4 559 руб.).
5. Пересчёт `totals` и сортировка — уже существующими функциями.

Каждое автоисправление добавляет строку в `report['guard_log']` (для журнала сервера;
в UI не выводится).

### А4. Отчёт полноты

В `report['completeness']`: `{'rows_total': N, 'rows_matched': M, 'rows_in_findings': K,
'follow_up_requests': X}`. UI показывает строку «Проверено строк: N · сопоставлено: M ·
в расхождениях: K» в сводке экспертного анализа.

## Б. Чистый вывод (static/index.html)

- Дубли уходят после А3.
- Строка контроля полноты (А4) в блоке сводки.
- Прочая структура таблицы не меняется (колонки «Документ | Влияние | Пояснение» — из прошлой задачи).

## Вне рамок этой спецификации

- Часть В: ревизия программной сверки — отдельный шаг: сначала отчёт о найденных проблемах,
  правки только по согласованию.
- Часть Г: расширение кеша структур (`col_profiles.json`) — после А–В.
- Production не трогаем; публикация только в staging.

## Тесты

- Юнит-тесты на каждый guard: дедупликация (в т.ч. после переклассификации), обнуление влияния пары,
  окно дат, исправление влияния confirmed_missing, полнота (`_find_unexplained_rows`),
  добавление программных `ambiguous`-строк.
- Дозапрос: мок клиента Claude, проверка объединения отчётов и лимита 2 дозапросов.
- Полный набор `python -m unittest discover -s tests -v` + проверка синтаксиса JS в `static/index.html`.

## Критерии приёмки

1. На проверенном примере находятся все 4 ранее пропущенные операции.
2. Дубль 4 559 руб. отсутствует.
3. У всех «Разница в датах» влияние 0 и окно соблюдено.
4. В сводке видна строка полноты.
5. 70 старых тестов + новые проходят; staging обновлён, `/api/health` показывает новый коммит.
