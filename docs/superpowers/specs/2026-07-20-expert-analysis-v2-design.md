# Экспертный анализ v2: программное сопоставление + вердикты Claude — дизайн

Дата: 2026-07-20. Пользователь дал карт-бланш: «текущий запрос удалить, перестроить как считаешь нужным».

## Проблемы v1 (подтверждены на реальном примере)

1. Claude сам перечислял строки и row_id → ошибки в evidence → guard понижал реальные пары
   в «Требуется проверка» с ненулевым влиянием (−9 900, −8 808, −8 000, −5 850).
2. Claude сам писал суммы влияния → мог ошибаться (случай 4 559).
3. Заголовки/категории противоречили друг другу («Нет у организации» внутри «Разницы в датах»).
4. Полнота достигалась дозапросами — дорого и ненадёжно.

## Принцип v2

**Программа считает — Claude судит.** Всё механическое (сопоставление по суммам, влияния,
окна дат, полнота) делает сервер детерминированно. Claude получает только спорные места
и выносит вердикты по выданным сервером идентификаторам. Выдумать строку или сумму невозможно.

## Конвейер

1. **Сбор строк** (как раньше): строки обеих сторон с id, суммами, датами; сальдо.
2. **Программное сопоставление**: жадное 1:1 по модулю суммы (допуск 0.01),
   предпочтение — то же семейство документа, затем минимальная разница дат.
   Результат: exact-пары (та же дата — не показываются), date-пары (`p1..`, сумма равна,
   даты различаются), несопоставленные строки (`u1..`). Строки меньше `min_amount` отбрасываются.
3. **Один запрос Claude** (только если есть спорные места): payload = сальдо, настройки,
   date-пары (с days/window/within_window) и несопоставленные строки. Ответ по схеме:
   - `pair_verdicts[]`: `date_pair` | `unrelated` | `needs_review` + note;
   - `unmatched_verdicts[]`: `missing` | `opening_balance_bridge` | `needs_review` + note;
   - `cross_matches[]`: две несопоставленные строки = одна операция
     (`amount_difference` | `sign_difference` | `date_pair`) + note;
   - `conclusion`, `confidence`.
4. **Сборка отчёта программой**:
   - влияние строки = `credit − debit` (одна формула для обеих сторон; это вклад
     в разницу конечного сальдо «контрагент − организация»);
   - date-пара: влияние всегда 0; в пределах окна → `likely_date_pair`,
     вне окна → `ambiguous` с текстом «разница N дн. превышает допуск M дн.»
     (окно: оплаты → date_window_payment, остальное → date_window_delivery);
     вердикт `unrelated` → пара распадается на два `confirmed_missing` с влияниями;
   - несопоставленная строка: по умолчанию и при `missing` → `confirmed_missing`
     с влиянием; `opening_balance_bridge` / `needs_review` → соответствующая категория,
     влияние сохраняется;
   - `cross_matches`: влияние пары = сумма влияний обеих строк (для `date_pair`
     требуются равные модули сумм, влияние 0 + проверка окна);
   - неизвестные id игнорируются; строки без вердикта получают поведение по умолчанию —
     полнота гарантирована конструкцией;
   - фильтры настроек: выключенный тип поиска скрывает соответствующую категорию;
   - контрольная сверка: `opening + Σ влияний ≈ closing`, расхождение — в `guard_log`;
   - `completeness`: rows_total / rows_matched (обе строки пар) / rows_in_findings.
5. Если спорных мест нет — отчёт собирается без запроса Claude (вывод программный).

## Контракт наружу не меняется

`run_independent_expert_analysis(df1, df2, client, model, settings)` →
`{'status', 'report', 'warnings', 'usage'}`; report: conclusion, confidence, balances,
totals, discrepancies (category/title/influence/reason/confidence/evidence/
resolved_evidence/clickable), completeness, guard_log. UI и main.py без изменений
(кроме уже существующей строки полноты).

## Удаляется из v1

Старый промпт-перечислитель, дозапросы, `resolve_expert_evidence`-фолбэки,
`_downgrade_false_confirmed_missing`, guard-понижения, дедупликация
(дубли невозможны конструкцией).
